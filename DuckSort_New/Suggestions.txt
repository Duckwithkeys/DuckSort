────────────────────────────────────────────────────────────────────────────────
🔴 [VM-1] 20+ @Published didSets each call updateDerivedState() with no coalescing
Lines: 77–208 (filter property didSets)
────────────────────────────────────────────────────────────────────────────────
Every one of the ~20 filter properties (filterRule, selectedTagFilters,
selectedRatings, sortOrder, filterEditedActive, filterRawActive, etc.) calls
updateDerivedState() directly in their didSet. resetFilterPopover() sets ~10 of
these in a row, triggering 10 full filter+sort+animation passes back-to-back.

updateDerivedState() is O(n) — it iterates the entire photoSets array, runs tag
lookups per photo, does an O(n log n) sort, and fires a Spring animation.
Running it 10 times in sequence for a single "reset filters" action wastes ~9x
the work.

FIX: Add a dirty-flag coalescing guard:

  private var derivedStateDirty = false

  private func setNeedsDerivedUpdate() {
      guard !derivedStateDirty else { return }
      derivedStateDirty = true
      Task { @MainActor [weak self] in
          self?.derivedStateDirty = false
          self?.updateDerivedState()
      }
  }

Replace every `didSet { updateDerivedState() }` with
`didSet { setNeedsDerivedUpdate() }`. Also update resetFilterPopover() and
clearAllFilters() to use batchUpdate{} or a suppress flag so the whole reset
costs exactly 1 filter pass.

🔴 [VM-2] photoSets didSet chains 3 expensive O(n) passes on every mutation
Lines: 35–41
────────────────────────────────────────────────────────────────────────────────
Every assignment to `photoSets` (including single-element mutations like
selection toggles) triggers all three of:
  • rebuildPhotoSetIndex()   — O(n) dictionary rebuild
  • updateGlobalCounts()     — O(n) stats + folder tree rebuild
  • updateDerivedState()     — O(n) filter+sort + Spring animation

Selection toggles, rating changes, and tag assignments all write to photoSets
and pay this full cost. On a 5,000-photo library each keypress costs 3 full O(n)
passes and a layout animation.

FIX: Separate "selection/rating mutations" (cheap — only update counters) from
"data mutations" (require full pipeline). Add a fast path:

  // Fast path: only update selection-derived counters, no sort/animate
  func updateSelectionCounters() {
      cachedSelectedCount = photoSets.count(where: \.isSelected)
      objectWillChange.send()
  }

Use this for toggleSelection/selectAll/deselectAll instead of triggering the
full photoSets didSet chain.

🔴 [VM-3] applyMetadataAndTagResults causes 4–6 full pipeline runs per load
Lines: 739–786
────────────────────────────────────────────────────────────────────────────────
The batch metadata apply does:
  1. self.photoMetadata = metadataCache    → clears photoDateCache
  2. tagStore.setTagsBatch(batchTags)     → fires objectWillChange
                                             → async Task → updateGlobalCounts
                                                          → updateDerivedState
  3. self.photoSets = updatedSets         → didSet → 3-pass pipeline

This sequence happens twice (phase 1: first 100, phase 2: rest). Total: ≥6 full
O(n) pipeline runs per library load, all blocking main actor work.

FIX: Wrap the entire apply block in batchUpdate{} and use a suppressDerivedUpdates
flag so only one updateDerivedState() runs at the end:

  func applyMetadataAndTagResults(...) {
      suppressDerivedUpdates = true
      self.photoMetadata = metadataCache
      self.photoSets = updatedSets
      tagStore.setTagsBatch(batchTags, suppressNotifications: true)
      suppressDerivedUpdates = false
      updateGlobalCounts()
      updateDerivedState()
  }

────────────────────────────────────────────────────────────────────────────────
🔴 [GRID-1] AsyncSemaphore in ThumbnailView cancels the WRONG waiter — hung tasks
Lines: ThumbnailView.swift, cancelWaiter() ~line 298–308
────────────────────────────────────────────────────────────────────────────────
When a task is cancelled while waiting for the semaphore, cancelWaiter() removes
the LAST waiter in the queue, not the cancelled one. This means:
  1. The cancelled task's continuation is leaked — never resumed → hangs forever
  2. An innocent, non-cancelled task gets erroneously cancelled

Over time, as the user scrolls quickly, hung continuations accumulate, exhausting
semaphore slots. Throughput silently degrades below 1 concurrent decode.
Thumbnails appear to stop loading even though the code appears to be running.

FIX: Track waiters with identity. Use `[(id: ObjectIdentifier, continuation)]`
and match on cancel by task identity. Or replace the custom semaphore with
TaskGroup(maxConcurrentOperations:).

────────────────────────────────────────────────────────────────────────────────
🔴 [GRID-2] Semaphore limit of 32 concurrent decodes causes CPU/IO thrash
Lines: ThumbnailView.swift line ~115
────────────────────────────────────────────────────────────────────────────────
32 simultaneous CGImageSource decodes saturates CPU cores and causes memory
pressure and cache thrashing, making each individual decode slower, not faster.
The original comment said "limit: 4" — the limit was raised to 32 without
explanation.

FIX: Drop to 4–8 concurrent decodes:
  let semaphore = AsyncSemaphore(limit: max(4, ProcessInfo.processInfo.processorCount / 2))

────────────────────────────────────────────────────────────────────────────────
🔴 [GRID-3] 128px proxy cached as 600px — grid shows blurry thumbnails forever
Lines: ThumbnailView.swift lines ~75–91
────────────────────────────────────────────────────────────────────────────────
During scrolling, a 128px "fast proxy" is fetched and stored in ThumbnailCache
using the URL-only key. When scrolling stops, the code requests the full 600×600
thumbnail — but because ThumbnailCache uses URL-only keys, the cached 128px image
is returned as an immediate cache hit. The 600px version is never decoded.
The grid permanently displays stretched 128px thumbnails.

FIX: Use a compound cache key of (url, targetPixelSize) for ThumbnailCache, so
128px and 600px results occupy different entries. Or: skip the 128px proxy
entirely and just wait for the scroll to settle before decoding at full size (the
loading spinner is acceptable during rapid scroll).

────────────────────────────────────────────────────────────────────────────────
🟠 [GRID-4] ThumbnailCache cost computed in points, not pixels — 4× underreporting on Retina
Lines: ThumbnailView.swift, ThumbnailCache.insert() ~line 259–262
────────────────────────────────────────────────────────────────────────────────
`NSImage.size` is in points. On a 2× Retina display, cost is underreported by
4× (2² = 4), making the cache totalCostLimit 4× more permissive than intended.
The cache can silently consume 800MB–1.6GB on Retina Macs, causing memory
pressure that slows everything else down.

FIX: Use pixel dimensions:
  let rep = image.representations.first
  let pw = rep?.pixelsWide ?? Int(image.size.width)
  let ph = rep?.pixelsHigh ?? Int(image.size.height)
  let cost = pw * ph * 4
